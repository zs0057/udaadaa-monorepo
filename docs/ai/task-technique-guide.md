# Task Technique Guide

## 목적

AI 기법을 모든 작업에 기계적으로 적용하지 않고, 작업의 성격과 위험도에 따라 적절한 기법을 선택한다.

## 기법 요약

- **Harness Engineering:** 큰 작업을 역할이 다른 여러 단계로 나누고 각 단계의 입력, 출력과 검증 기준을 정의한다.
- **ReAct:** 코드 검색, 문서 조회, 명령 실행과 같은 행동의 결과를 다음 분석에 반영한다.
- **Self-Consistency:** 중요한 판단을 여러 독립적인 관점에서 검토하고 공통 결론과 차이를 비교한다.
- **Memory & Compaction:** 장기 작업에서 반드시 보존할 정보와 요약 가능한 정보를 구분한다.
- **단계별 검토:** 복잡한 규칙을 사실 확인, 규칙 적용, 결과 검증 순서로 처리한다.

## 업무 유형별 선택

| 업무 유형 | 주요 기법 | 적용 방법 | 선택 근거 |
|---|---|---|---|
| 전체 아키텍처 설계 | Harness Engineering + Self-Consistency | 요구사항, 제약, 후보 설계, 관점별 검증, ADR 작성으로 분리 | 작업 범위가 크고 정답이 하나가 아니므로 단계를 나누고 여러 관점에서 설계 누락과 편향을 줄여야 한다. |
| 기존 시스템 분석 | ReAct | 실제 코드와 설정을 검색하고 발견한 결과를 다음 조사에 반영 | 기존 시스템의 실제 동작은 코드와 설정에 있으므로 기억이나 추측보다 조회 결과를 근거로 분석해야 한다. |
| 도메인 및 모듈 분리 | Harness Engineering + 단계별 검토 | 기능, 규칙, 데이터 소유권, 의존성, 경계를 순서대로 분석 | 기능 이름만으로 경계를 정하면 책임이 섞일 수 있으므로 비즈니스 규칙과 데이터 소유권을 순차적으로 확인해야 한다. |
| 기술적 사실 질문 | ReAct | 기억에 의존하지 않고 코드 또는 공식 문서를 확인한 후 답변 | 라이브러리 동작과 현재 코드는 변경될 수 있으므로 확인 가능한 근거를 조회하여 사실 오류를 줄여야 한다. |
| 중요한 기술 결정 | Self-Consistency | 개발, 운영, 보안, 정합성, 확장성 관점에서 독립 검토 | 한 관점의 장점만 보고 결정하면 다른 영역의 위험을 놓칠 수 있으므로 독립적인 관점의 결론을 비교해야 한다. |
| 구현 및 디버깅 | Harness Engineering + ReAct | 명세, 구현, 테스트, 오류 분석, 수정, 재검증의 반복 수행 | 구현은 여러 단계가 연결되고 오류 원인이 실행 결과에 따라 달라지므로 작업을 나누고 관찰 결과를 다음 수정에 반영해야 한다. |
| 코드 리뷰 | ReAct + Self-Consistency | 실제 변경을 확인하고 기능, 보안, 성능, 테스트 관점에서 검토 | 실제 diff와 테스트 결과를 근거로 확인하면서 서로 다른 품질 관점의 누락을 교차 검증해야 한다. |
| 장기 마이그레이션 | Memory & Compaction | 핵심 규칙과 결정은 보존하고 일시적인 탐색 과정은 요약 | 작업 기간이 길어질수록 핵심 결정이 묻히거나 잊힐 수 있으므로 재사용할 정보만 보존하고 나머지는 압축해야 한다. |

## 질문 유형별 처리

### 단순 사실 질문

- 관련 코드나 공식 문서를 직접 확인한다.
- 확인된 사실과 아직 확인하지 못한 내용을 구분한다.
- 불필요한 다중 관점 검토는 수행하지 않는다.

### 복잡한 비즈니스 규칙 질문

```text
1. 입력 사실 확인
2. 적용할 비즈니스 규칙 정리
3. 예외 조건 확인
4. 결과 도출
5. 경계값과 실패 사례 검증
```

### 중요한 기술 결정

- 최소 두 개 이상의 대안을 비교한다.
- 개발, 운영, 보안, 데이터 정합성, 확장성 관점에서 각각 검토한다.
- 선택한 이유와 포기한 장점을 ADR에 기록한다.

## 작업별 기본 파이프라인

### 현행 시스템 분석

```text
기능 목록 추출
→ 코드와 Supabase 의존성 연결
→ 데이터 흐름 분석
→ 누락 및 충돌 검증
→ 사람이 확인할 질문 정리
→ AS-IS 문서 반영
```

### 아키텍처 설계

```text
요구사항과 제약 수집
→ 품질 속성 우선순위 결정
→ 설계 후보 작성
→ 관점별 교차 검토
→ 사용자와 선택 합의
→ TO-BE 문서와 ADR 반영
```

### 구현

```text
완료 기준 정의
→ 관련 코드와 문서 확인
→ 테스트 작성 또는 검증 방법 결정
→ 최소 범위 구현
→ 테스트와 정적 검사
→ 변경 사항 자체 리뷰
→ 문서 갱신
```

## 컨텍스트 관리

### 반드시 보존할 정보

- 확정된 비즈니스 규칙
- 도메인 경계와 데이터 소유권
- API 계약과 DB 변경 사항
- 아키텍처 결정과 ADR
- 완료된 마이그레이션 범위
- 알려진 위험과 미해결 사항

### 요약 가능한 정보

- 단순 탐색 과정
- 실패한 임시 시도
- 반복된 대화와 로그
- 이미 해결되어 재현되지 않는 세부 오류

## 검증 원칙

- AI가 작성한 코드를 검토 없이 반영하지 않는다.
- 코드 관련 주장은 파일 위치와 실행 결과로 확인한다.
- 구현 결과는 가능한 경우 테스트, 빌드와 정적 분석으로 검증한다.
- 결제, 정산, 인증과 데이터 이전은 단일 관점의 답변으로 확정하지 않는다.
- AI가 제안하고 사람이 결정하며 자동화된 검증이 결과를 확인한다.
