# Udaadaa Backend Migration Overview

## 1. 문서 목적

이 문서는 Udaadaa 백엔드를 Supabase 중심 구조에서 Spring 기반 모듈형 모놀리스로 이전하는 이유와 기본 방향을 정의한다.

현재 Udaadaa는 Flutter 클라이언트가 Supabase의 Database, Auth, Realtime, Storage를 직접 사용하고 일부 서버 로직을 Edge Function으로 처리한다. 초기 서비스 개발에는 효율적이었지만, 실제 서비스 운영 과정에서 사용자로부터 채팅 전송과 수신이 간헐적으로 느리다는 피드백이 발생했다. 현재 구조는 채팅 처리 과정이 Flutter, Supabase Database, Realtime 및 Edge Function에 분산되어 있어 지연과 장애가 발생한 구간을 추적하고 복구하기 어렵다.

또한 향후 사용자와 트래픽이 증가하고 보증금, 결제 및 정산과 같은 기능이 추가되면 외부 플랫폼 의존성과 분산된 비즈니스 로직이 서비스 확장의 장애물이 될 수 있다. 따라서 단기적인 코드 수정에 그치지 않고, 핵심 비즈니스 로직과 운영 책임을 Spring 서버로 이전할 필요가 있다.

## 2. 마이그레이션 이유

### 2.1 백엔드 제어권 확보

- DB, 인증, Realtime 및 서버 장애 대응을 외부 플랫폼에 의존
- 외부 플랫폼 장애 발생 시 원인 파악과 즉각적인 대응에 한계
- Realtime 연결 상태와 재연결 정책을 서비스 요구사항에 맞게 제어하기 어려움
- 메시지 지연·누락 발생 시 복구 과정을 클라이언트에서 별도로 처리해야 함
- 로그와 모니터링 범위가 여러 Supabase 구성 요소와 Flutter에 분산됨
- 외부 플랫폼의 요금제, 사용량 제한 및 정책 변경에 영향을 받음
- 트래픽 증가에 맞춘 캐시, 메시지 큐 및 서버 확장 전략 적용에 제약

Udaadaa에서 채팅은 실시간 챌린지 진행과 사용자 동기 부여를 위한 핵심 기능이다. 따라서 채팅 연결과 메시지 복구를 외부 Realtime 서비스에만 의존하지 않고, 서비스에서 직접 관찰하고 제어할 수 있는 구조가 필요하다.

실제 사용자 피드백에서 확인된 간헐적인 채팅 지연은 단순한 사용성 문제를 넘어 챌린지 참여 경험과 사용자 간 상호작용을 저하시킬 수 있다. Spring 서버에서 메시지 처리 과정을 통합 관리하여 지연 구간을 측정하고, 연결 장애 시 재연결과 누락 메시지 복구 정책을 직접 적용할 수 있어야 한다.

### 2.2 비즈니스 로직 분리와 기능 확장

- Flutter에 UI, 데이터 접근 및 비즈니스 로직이 혼재
- `ChatCubit` 등 클라이언트 상태 관리 코드가 메시지, 읽음, 차단, 이미지 및 알림 로직까지 담당
- 비즈니스 규칙 변경 시 Flutter, Edge Function, RLS 및 Database Function을 함께 확인해야 함
- 분산된 로직으로 인해 단위 테스트와 통합 테스트 작성이 어려움
- 클라이언트가 DB를 직접 호출하여 서버 차원의 일관된 권한 검증과 트랜잭션 관리에 한계
- 채팅, 챌린지 및 기록 로직을 Spring 서버에서 통합 관리할 필요
- 향후 보증금 결제, 환급, 몰수 및 정산 기능의 안전한 확장 필요
- 중복 결제와 중복 환급 방지 및 감사 로그 관리 필요
- 관리자 기능과 외부 결제 시스템 연동을 위한 백엔드 기반 필요

Supabase에서도 Edge Function, RLS 및 Database Function을 이용해 비즈니스 로직을 분리할 수 있다. 그러나 기능이 복잡해질수록 로직이 여러 실행 환경에 분산된다. Spring 서버를 중심으로 비즈니스 규칙과 트랜잭션을 관리하여 책임을 명확히 하고 유지보수성과 테스트 가능성을 높인다.

현재 구조를 유지한 상태에서 기능을 계속 추가하면 Flutter의 상태 관리 코드와 Supabase의 여러 구성 요소가 함께 복잡해지고, 하나의 정책 변경이 여러 실행 환경에 영향을 주게 된다. 특히 금전 데이터를 다루는 보증금 기능은 권한 검증, 중복 처리 방지, 트랜잭션 및 감사 로그가 필요하므로 서버 중심의 일관된 처리가 필수적이다.

### 2.3 마이그레이션 필요성

- 사용자 피드백을 통해 간헐적인 채팅 지연 문제 확인
- 채팅이 핵심 기능이므로 연결 지연과 메시지 누락이 서비스 경험에 직접적인 영향
- 분산된 처리 구조로 인해 지연 및 장애 원인의 추적과 복구가 어려움
- 사용자와 트래픽 증가 시 Realtime 연결 및 메시지 처리 복잡도 증가
- 기능 추가가 Flutter, Edge Function, RLS 및 Database Function의 동시 변경으로 이어짐
- 보증금, 결제 및 정산 도입 시 서버 중심의 권한 검증과 트랜잭션 관리 필요
- 현재 구조의 부분적인 개선만으로는 운영 제어권과 비즈니스 로직 분산 문제를 함께 해결하기 어려움

이에 따라 Udaadaa의 안정적인 운영과 기능 확장을 위해 Spring 기반 백엔드로의 점진적 마이그레이션이 필요하다.

## 3. 마이그레이션 목표

- Flutter는 화면 표시와 사용자 입력 처리에 집중
- Spring은 인증, 권한 검증, 비즈니스 규칙 및 트랜잭션 관리 담당
- PostgreSQL을 서비스 데이터의 최종 원본으로 사용
- 채팅 연결이 끊겨도 저장된 데이터를 기준으로 누락 메시지 복구
- 도메인별 책임을 분리한 모듈형 모놀리스 구성
- 기능 단위의 점진적 이전으로 서비스 중단과 데이터 유실 방지
- 향후 보증금과 정산 기능을 확장할 수 있는 기반 마련

## 4. 기본 마이그레이션 방향

- 초기 아키텍처는 Spring 기반 모듈형 모놀리스로 구성한다.
- 기존 서비스를 한 번에 교체하지 않고 도메인 단위로 점진적으로 이전한다.
- 초기에는 Spring이 기존 Supabase PostgreSQL과 Supabase JWT를 사용한다.
- 각 기능의 읽기와 쓰기를 검증한 후 Flutter의 Supabase 직접 호출을 Spring API로 교체한다.
- 동일 기능을 Flutter와 Spring이 동시에 수정하는 이중 쓰기를 피한다.
- 모든 기능 전환 후 Realtime, Edge Function, Auth, Storage 및 Database 의존성을 순차적으로 제거한다.
