# ADR-001 초기 기술 결정

> 상태: 승인됨  
> 결정일: 2026-07-27

## 1. ADR이란

ADR(Architecture Decision Record)은 중요한 기술 결정을 나중에도 이해할 수 있도록 기록하는 문서다.

단순히 선택 결과만 적지 않고 다음 내용을 함께 남긴다.

- 어떤 문제를 결정했는가
- 무엇을 선택했는가
- 왜 선택했는가
- 선택으로 생기는 제약은 무엇인가
- 언제 다시 검토할 것인가

## 2. 결정 배경

Udaadaa는 기존 Flutter·Supabase 구조를 Spring 기반 모듈형 모놀리스로 점진적으로 이전한다. 초기 마이그레이션에서는 완성도 높은 분산 시스템을 미리 만드는 것보다 구현과 운영을 단순하게 유지하는 것이 중요하다.

따라서 현재 서비스 규모에서 필요한 안정성과 제어권을 확보하되, Kafka·RabbitMQ 같은 별도 인프라와 불필요한 데이터베이스 분리는 초기 범위에서 제외한다.

## 3. 결정 내용

| 항목 | 초기 결정 | 선택 이유 |
|---|---|---|
| WebSocket 프로토콜 | STOMP 사용 | Spring의 지원을 활용해 구독·발행 구조를 빠르고 일관되게 구현할 수 있음 |
| 이미지 업로드 | Spring이 권한·경로를 발급하고 Flutter가 Supabase Storage에 제한적으로 직접 업로드 | 파일을 Spring이 중계하는 부하를 피하면서 업로드 권한은 서버가 통제할 수 있음 |
| 모듈 연결 | 동기 내부 메서드와 Spring 내부 이벤트 사용 | 같은 애플리케이션 안에서 불필요한 네트워크와 메시지 인프라 없이 책임을 분리할 수 있음 |
| 이벤트 유실 방지 | 초기에는 Outbox를 사용하지 않음 | 초기 복잡도를 낮추고, 유실 방지가 실제로 필요한 기능이 생길 때 도입하기 위함 |
| DB Schema | 기존 단일 PostgreSQL Schema 유지 | 기존 Supabase DB를 그대로 활용하고 초기 Schema 이전 범위를 줄이기 위함 |
| 메시지 순서·읽음 | 서버 BIGINT 순번과 방별 마지막 읽음 순번 사용 | 생성 시각 충돌과 클라이언트 시간 차이를 피하고 조회·복구·미읽음 계산을 단순화함 |
| 회원 탈퇴 | 상태 전환과 재시도 방식 사용 | 로컬 데이터 처리와 외부 Supabase Auth 삭제가 일부 실패해도 복구할 수 있음 |
| 모듈 경계 검증 | Spring Modulith 사용 | 모듈 간 잘못된 의존성을 자동으로 검사하고 모듈형 모놀리스의 경계를 유지하기 위함 |

## 4. 세부 적용 기준

### 4.1 STOMP

- Flutter는 인증된 WebSocket 연결을 생성한다.
- 채팅방 단위 목적지를 구독하고 새 메시지를 수신한다.
- 메시지 생성 자체는 REST API로 요청한다.
- STOMP는 실시간 전달을 담당하고 PostgreSQL과 REST API는 저장·조회·누락 복구를 담당한다.
- 연결이 끊기면 Flutter가 재연결한 후 마지막으로 확인한 순번 이후의 메시지를 REST API로 조회한다.

### 4.2 이미지 업로드

```text
Flutter → Spring에 업로드 요청
→ Spring이 사용자·방·기록 권한과 파일 조건 확인
→ Spring이 허용된 Storage 경로와 제한된 업로드 정보 반환
→ Flutter가 Supabase Storage에 직접 업로드
→ Flutter가 Spring에 업로드된 파일 참조 제출
→ Spring이 파일 참조를 검증한 뒤 업무 데이터 저장
```

- Flutter가 임의의 사용자 또는 채팅방 경로를 정하지 않는다.
- Spring이 허용 경로, 파일 크기와 MIME 타입을 결정한다.
- 업로드 후 업무 데이터 저장이 실패한 파일은 임시 파일 정리 또는 만료 대상으로 관리한다.
- 실제 구현 전에는 현재 Supabase Storage가 제공하는 제한 업로드 방식과 보안 정책을 공식 문서로 다시 확인한다.

### 4.3 내부 메서드와 내부 이벤트

- 함께 성공하거나 실패해야 하는 작업은 내부 Application Service와 하나의 DB 트랜잭션으로 처리한다.
- WebSocket 전달과 Push처럼 핵심 데이터 저장 이후 실행할 수 있는 작업은 commit 이후 내부 이벤트로 처리한다.
- 초기에는 Kafka·RabbitMQ를 사용하지 않는다.

### 4.4 Outbox 도입 시점

다음 조건 중 하나가 발생하면 Outbox 도입을 다시 검토한다.

- 결제·환급·정산 이벤트를 반드시 보존해야 함
- Spring 서버가 여러 인스턴스로 확장됨
- 외부 메시지 브로커를 사용함
- 서버 재시작 중에도 후속 이벤트의 유실을 허용할 수 없음

채팅 WebSocket 전달이 누락된 경우에는 Outbox보다 PostgreSQL과 REST API의 누락 메시지 복구를 우선 사용한다.

### 4.5 단일 DB Schema와 모듈 경계

- 기존 Supabase PostgreSQL의 Schema를 초기에는 물리적으로 분리하지 않는다.
- 각 테이블의 쓰기 책임은 하나의 Spring 모듈에만 둔다.
- 다른 모듈의 Repository와 Entity를 직접 참조하지 않는다.
- Spring Modulith 검증으로 잘못된 모듈 의존성을 확인한다.
- DB 권한의 물리적 분리 또는 서비스 분리가 필요해질 때 모듈별 Schema를 다시 검토한다.

### 4.6 메시지 순서와 읽음 위치

- 외부 식별용 `messageId`는 UUID를 사용한다.
- 서버 정렬용 `sequence`는 BIGINT를 사용한다.
- 클라이언트 재시도 중복 방지용 `clientMessageId`를 별도로 둔다.
- 읽음 위치는 사용자와 채팅방별 `lastReadSequence BIGINT`로 저장한다.
- 정확한 테이블·인덱스·순번 생성 범위는 Chat 데이터 모델을 설계할 때 확정한다.

초기 권장안은 전체 메시지에 증가하는 BIGINT 순번을 사용하는 것이다. 방별 순번이 반드시 필요한 성능 또는 업무 요구가 확인되면 다시 검토한다.

### 4.7 회원 탈퇴

```text
ACTIVE
→ WITHDRAWAL_PENDING
→ WITHDRAWN
```

- 탈퇴 요청을 받으면 먼저 `WITHDRAWAL_PENDING`으로 변경하여 추가 쓰기를 제한한다.
- 삭제, 익명화와 보존 대상 데이터를 분류하여 처리한다.
- 로컬 데이터 처리가 완료되면 Supabase 세션과 Auth 사용자 삭제를 시도한다.
- 외부 Auth 삭제가 실패하면 실패 상태와 원인을 기록하고 재시도한다.
- 결제·정산·감사 데이터의 보존 기간은 관련 정책과 법적 요구사항을 확인한 후 별도로 결정한다.

## 5. 감수하는 제약

- STOMP에 맞춘 Flutter 클라이언트 구현과 라이브러리 검증이 필요하다.
- 제한된 직접 업로드는 Storage 정책과 Spring의 업로드 승인 정보가 함께 안전해야 한다.
- 내부 이벤트만 사용하면 서버가 종료되는 순간 후속 이벤트가 유실될 수 있다.
- 단일 Schema는 DB 권한만으로 모듈 소유권을 강제하기 어렵다.
- 회원 탈퇴가 즉시 완료되지 않고 처리 대기 상태에 머물 수 있다.

## 6. 구현 전 확인 사항

- Spring Boot 버전과 호환되는 Spring Modulith 버전
- Flutter에서 사용할 STOMP 라이브러리의 유지보수 상태와 재연결 동작
- JWT를 사용하는 STOMP 연결·구독 권한 검증 방식
- 현재 Supabase Storage의 제한 업로드 지원 방식과 RLS 정책
- 메시지 BIGINT 순번의 생성 범위와 인덱스
- 회원 데이터의 삭제·익명화·보존 기준

이 항목들은 이번 ADR의 방향을 바꾸지 않는 구현 세부사항이다. 조사 결과 현재 선택이 과도한 제약이나 보안 문제를 만든다면 별도 ADR에서 결정을 변경한다.
