# ADR-002 Supabase 인프라 제거 시점 결정

> 상태: 채택
> 작성일: 2026-07-28
> 결정 여부: 대안 B 채택

## 1. 결정할 문제

Udaadaa의 최종 목표는 Supabase Auth, Database, Realtime, Storage와 Edge Function에 대한 직접 의존성을 제거하고 Spring을 백엔드의 중심으로 만드는 것이다.

이 문서에서는 Supabase를 제거할지 여부가 아니라 **어느 시점과 방식으로 제거하는 것이 개발 리소스, 기존 자산 호환성, 운영 위험과 사용자 영향 측면에서 유리한지** 결정한다.

비교 대상은 다음 세 가지다.

- 대안 B: Spring을 Supabase에 먼저 연결하고 안정화 후 인프라 제거
- 대안 C: 독립 PostgreSQL을 먼저 준비하고 도메인별로 Supabase 제거
- 대안 D: 전체 시스템을 새로 구축한 뒤 한 번에 Supabase 제거

Supabase를 최종 인프라로 계속 사용하는 대안 A는 완전 제거라는 목표와 맞지 않아 비교 대상에서 제외한다.

## 2. 비교를 위한 현재 가정

### 서비스 가정

- 누적 가입자: 3,000명
- MAU: 2,500명
- DAU: 1,000명
- 목표 채팅 메시지: 일 10,000개
- 목표 최대 WebSocket 연결: 1,000개
- 응답 지연 허용 범위: 약 1~2초
- 챌린지는 2주 동안 매일 진행되므로 평상시 서비스 중단은 허용하지 않는다.
- 불가피한 전환은 이용량이 낮은 새벽 1시에 수행한다.
- 전환 중에도 진행 중인 챌린지와 제출 데이터가 유실되어서는 안 된다.
- Auth 전환 시 기존 세션 유지 또는 재로그인 안내가 필요하다.

### 현재 Inventory

- Public 테이블: 14개
- View: 1개
- DB Function: 2개
- Storage Bucket: 3개
- 배포 활성 Edge Function: 5개
- 채팅 Realtime 이벤트: 4개
- Flutter Cubit이 Supabase를 직접 호출하는 구조
- 계획 DB Storage: 초기 20GB
- 계획 Object Storage 정상 상태: 약 439GB
- 계획 메시지: 일 10,000개

이 수치는 실제 운영 지표가 아니라 마이그레이션을 학습·설계하기 위한 계획 가정이다. Database와 Storage 이전 시간은 사용자 수보다 메시지·기록 행 수, 이미지 개수와 전체 용량에 더 크게 좌우된다.

## 3. 공통 호환성 기준

다음 호환성은 제품 선정과 POC 이전의 **계획 추정치**다. 실제 이전 가능 여부를 보장하는 수치가 아니다.

| 구성 요소 | 독립 인프라로의 예상 호환성 | 그대로 가져갈 수 있는 부분 | 다시 구현하거나 변환할 부분 |
|---|---:|---|---|
| Public PostgreSQL 데이터 | 높음, 70~90% | 일반 테이블, 행, 인덱스, 기본 제약 조건 | Supabase 역할, 권한, 일부 Extension과 소유권 |
| RLS·DB Function·Trigger | 중간, 40~70% | PostgreSQL SQL과 업무 규칙 일부 | `auth.uid()`, Supabase 역할, Realtime·Webhook 결합 |
| Supabase Auth | 낮음~중간, 30~60% | 사용자 ID, 이메일, metadata와 password hash의 이전 가능성 | 대상 Auth별 hash 지원, OAuth 연결, 세션과 JWT 전환 |
| Supabase Storage 객체 | 파일 높음, 80~95% | 원본 파일과 객체 경로 | Bucket 정책, RLS, 공개·서명 URL과 metadata 연결 |
| Supabase Realtime | 낮음, 0~20% | 이벤트 종류와 처리 요구사항 | 채널 구독, 재연결, 메시지 전달을 STOMP로 재구현 |
| Edge Function | 중간, 40~70% | 업무 규칙과 외부 API 호출 의도 | Deno 실행 코드, 배포 환경과 비밀 관리의 Spring 이전 |
| Flutter Supabase 호출 | 낮음, 0~30% | 모델과 일부 화면 흐름 | Data API·RPC·Realtime 호출을 REST·STOMP로 교체 |

### 호환성 해석

- Supabase Database는 PostgreSQL이므로 일반 업무 데이터의 이동 가능성은 높다.
- `auth.uid()`, Supabase 전용 역할, Storage Schema와 Realtime publication은 일반 PostgreSQL에 그대로 적용되지 않는다.
- Auth 사용자와 password hash는 추출할 수 있어도 새 Auth 제품이 같은 hash 가져오기를 지원하는지는 별도 확인해야 한다.
- Auth 서명 키나 세션 체계가 달라지면 기존 로그인 세션은 유지되지 않아 누적 계정 3,000명에게 재로그인이 필요할 수 있다.
- Storage는 S3 호환 도구로 객체 복사가 가능하지만 기존 Supabase URL과 RLS 정책은 새 Storage에서 다시 설계해야 한다.
- Realtime과 Edge Function은 데이터 복사보다 애플리케이션 재구현에 가깝다.

## 4. 리소스 산정 기준

아래 범위는 현재 Inventory와 누적 가입자 3,000명·DAU 1,000명 계획을 기준으로 한 초기 계획치다.

- 1명의 백엔드 중심 개발자가 수행한다고 가정한다.
- Flutter 수정, 이전 스크립트, 기본 자동 테스트와 문서화를 포함한다.
- 제품 계약, 심사, 운영 장애와 대규모 데이터 전송 시간은 포함하지 않는다.
- `인주`는 한 사람이 한 주 동안 수행하는 작업량을 의미하며 일정 확정값이 아니다.
- 실제 데이터량과 Auth·Storage POC 결과에 따라 범위가 달라진다.

## 5. 대안 B: Spring 안정화 후 Supabase 제거

### 방식

```text
1차
Flutter 직접 접근 → Spring → 기존 Supabase

2차
Spring → 독립 Auth·PostgreSQL·Storage
```

### 예상 리소스

| 작업 | 초기 계획치 |
|---|---:|
| Spring API·STOMP와 기존 Supabase 연동 | 8~12인주 |
| 독립 DB·Auth·Storage 구축과 데이터 이전 | 6~10인주 |
| 두 번째 Flutter·운영 전환과 회귀 검증 | 2~4인주 |
| 총계 | 16~26인주 |

### Supabase 호환성

- 1차 전환에서는 기존 Database, Auth와 Storage를 유지하므로 호환성이 가장 높다.
- 기존 사용자 세션과 이미지 URL을 즉시 바꾸지 않아도 된다.
- Spring이 Supabase PostgreSQL의 기존 Schema, Function과 Auth ID에 맞춰 구현될 가능성이 높다.
- 2차 전환에서는 C·D와 같은 Auth·데이터·파일 이전 문제가 다시 발생한다.

### 사용자 영향

- 1차 영향: 낮음. 로그인과 기존 데이터·이미지 경로를 유지할 수 있다.
- 2차 영향: 중간. Auth 방식에 따라 누적 계정 3,000명에게 재로그인 또는 계정 복구 안내가 필요하다.
- 인프라 이전을 뒤로 미루므로 사용자 영향도 뒤로 미뤄질 뿐 사라지지는 않는다.

### 장단점

- 장점: Spring 문제와 인프라 이전 문제를 분리하여 장애 원인을 찾기 쉽다.
- 장점: 초기 롤백과 기존 사용자 경험 유지가 가장 쉽다.
- 단점: Spring 전환과 인프라 전환을 두 번 수행한다.
- 단점: Supabase 전용 Schema와 사용자 ID 구조가 새 코드에 고착될 수 있다.
- 단점: 전체 개발 리소스와 마이그레이션 기간이 가장 길어질 수 있다.

## 6. 대안 C: 독립 PostgreSQL 기반 도메인별 제거

### 방식

```text
이전하지 않은 도메인
Flutter → 기존 Supabase

이전한 도메인
Flutter → Spring → 독립 PostgreSQL

모든 도메인 전환 후
Supabase Auth·Storage와 잔여 기능 제거
```

### 예상 리소스

| 작업 | 초기 계획치 |
|---|---:|
| 독립 Spring·PostgreSQL 공통 기반 | 3~5인주 |
| 도메인별 Schema·API·데이터 백필·전환 | 8~13인주 |
| Auth·Storage·Realtime 제거와 최종 검증 | 3~6인주 |
| 총계 | 14~24인주 |

### Supabase 호환성

- 일반 PostgreSQL 데이터는 비교적 재사용하기 쉽지만 Supabase RLS와 Function은 Spring 권한·서비스 로직으로 변환해야 한다.
- 기존 UUID를 새 DB에서도 유지하면 회원과 도메인 데이터 연결 비용을 줄일 수 있다.
- 전환되지 않은 도메인은 기존 Supabase와 완전히 호환된다.
- 전환된 도메인은 최종 구조를 사용하므로 Supabase 호환성을 유지할 필요가 없다.
- 도메인 사이의 FK와 transaction이 강하게 연결되어 있으면 함께 전환해야 하므로 실제 도메인별 분리 가능성을 먼저 검증해야 한다.

### 사용자 영향

- 영향 범위가 도메인별로 나뉘므로 전체 사용자에게 한 번에 장애가 발생할 가능성이 낮다.
- Auth를 마지막까지 임시 유지하면 초기 재로그인을 피할 수 있다.
- Auth를 교체하는 최종 시점에는 누적 계정 3,000명의 세션 전환 문제가 남는다.
- 짧은 도메인별 쓰기 중단을 허용하면 이중 쓰기 없이 정합성을 관리할 수 있다.

### 장단점

- 장점: 새 Spring 기능을 최종 DB 구조에 바로 구현한다.
- 장점: 전환된 도메인부터 Supabase 의존성과 장애 범위가 줄어든다.
- 장점: 전체 재작성보다 사용자 영향과 롤백 범위를 작게 유지할 수 있다.
- 단점: 마이그레이션 기간에 Supabase와 독립 PostgreSQL을 함께 운영한다.
- 단점: 두 DB 사이의 데이터 소유권과 도메인 간 참조를 엄격하게 관리해야 한다.
- 단점: 도메인 경계가 잘못되면 임시 조회 연동이나 복잡한 데이터 동기화가 필요할 수 있다.

## 7. 대안 D: 전체 재구축 후 일괄 제거

### 방식

```text
기존 서비스
Flutter → Supabase

별도 신규 시스템 구축
새 Flutter 경로 → Spring → 독립 Auth·PostgreSQL·Storage

완료 후 전체 데이터 이전과 일괄 전환
```

### 예상 리소스

| 작업 | 초기 계획치 |
|---|---:|
| 전체 Spring·DB·Auth·Storage 구축 | 10~16인주 |
| 전체 데이터·파일·계정 이전 도구 | 4~7인주 |
| 전체 E2E·부하·전환·롤백 검증 | 3~6인주 |
| 총계 | 17~29인주 |

### Supabase 호환성

- 새 시스템은 Supabase 호환성을 거의 고려하지 않고 목표 모델로 설계할 수 있다.
- 그러나 최종 전환 때 기존 데이터, 사용자 ID, 파일 경로와 업무 결과를 모두 변환해야 한다.
- 기존 시스템과 신규 시스템을 장기간 동시에 개발하므로 양쪽 기능 차이를 계속 추적해야 한다.
- 데이터 자체의 PostgreSQL 호환성은 C와 같지만 일괄 전환으로 검증 범위가 커진다.

### 사용자 영향

- 개발 중 사용자 영향은 낮다.
- 최종 전환 시 영향이 전체 사용자에게 집중된다.
- Auth 세션, 이미지 URL 또는 데이터 정합성 문제가 생기면 모든 사용자가 동시에 영향을 받을 수 있다.
- 충분한 점검 시간, 사전 리허설과 전체 롤백 계획이 필요하다.

### 장단점

- 장점: 레거시 구조에 맞추지 않고 목표 시스템을 설계하기 쉽다.
- 장점: 전환 이후 임시 구조가 적다.
- 단점: 가장 오랫동안 실제 사용자 검증 없이 신규 시스템을 개발하게 된다.
- 단점: 전체 데이터의 마지막 변경분을 한 번에 동기화해야 한다.
- 단점: 전환 실패의 영향과 롤백 범위가 가장 크다.

### 8.1 대안 B와 C 중 어느 쪽이 유리한가

| Udaadaa 판단 기준 | 더 유리한 대안 | 이유 |
|---|---|---|
| 초기 개발 속도 | B | 기존 Auth·DB·Storage를 유지하므로 Spring API와 STOMP에 집중할 수 있음 |
| 기존 사용자 세션 유지 | B | Supabase Auth와 기존 UUID를 초기에는 변경하지 않음 |
| 기존 이미지 URL 호환 | B | Storage 경로와 Public URL을 초기에는 유지함 |
| 장애 원인 추적 | B | Spring 전환 오류와 인프라 이전 오류를 서로 다른 단계에서 검증함 |
| 기능별 롤백 | B | DB와 Storage를 유지한 상태에서 API 경로를 기능별로 되돌릴 수 있음 |
| 2주 챌린지 연속성 | B | 전환 범위가 작고 진행 중인 데이터의 저장 위치가 즉시 바뀌지 않음 |
| 초기 운영비 | B | 약 $105~113/월로 C의 AWS 비용과 Supabase 병행 비용보다 낮음 |
| Supabase 의존성 제거 속도 | C | 이전한 도메인은 바로 독립 PostgreSQL을 사용함 |
| 최종 DB 구조에 바로 구현 | C | 신규 기능을 중간 DB가 아닌 목표 DB에서 시작함 |
| 전체 예상 개발량 | C | B의 두 번째 인프라 이전이 없어 계획상 2인주 정도 작을 수 있음 |
| DB 운영 제어권 확보 속도 | C | 초기부터 백업·가용성·모니터링 정책을 직접 선택함 |

대안 B는 **초기 안정성, 호환성과 롤백**에서 유리하다. 대안 C는 **Supabase 제거 속도와 최종 구조 도달 속도**에서 유리하다.

### 8.2 대안 B 선택으로 감수하는 비용

- 1차 Spring 전환 후 독립 Auth·DB·Storage로 옮기는 2차 마이그레이션이 필요하다.
- 2차 마이그레이션에는 약 8~14인주가 추가로 필요하다.
- 중간 단계에서 Spring과 Supabase 비용을 함께 지불한다.
- 종료 조건을 정하지 않으면 중간 구조가 장기화되고 Supabase 의존성이 다시 고착될 수 있다.
- 1차 단계에서는 Supabase 인프라 장애의 영향을 계속 받으므로 인프라 제어권 확보는 완료되지 않는다.

## 9. 최종 해석

- Udaadaa의 1차 목표는 Flutter에서 비즈니스 로직을 분리하고 채팅 저장·전달·복구를 Spring에서 제어하는 것이다.
- Udaadaa의 2차 목표는 Supabase Auth·DB·Storage를 제거하여 인프라 제어권을 확보하는 것이다.
- 2주 챌린지가 진행되는 서비스에서는 최종 구조에 빨리 도달하는 것보다 전환 중 데이터 유실과 전체 장애를 피하는 것이 우선이다.
- 따라서 초기 안전성과 기존 호환성이 가장 높은 대안 B를 선택하고, 두 번째 인프라 이전 비용을 계획에 포함한다.
- 대안 C는 개발 인력과 두 DB 정합성 운영 역량을 확보하거나 Supabase 제거 일정이 안정성보다 중요해질 때 재검토한다.
- 대안 D는 전체 전환 위험이 사용자와 진행 중 챌린지에 집중되므로 현재 조건에서는 제외한다.

대안 B의 상세 비용과 성능 가정은 [ADR-003](ADR-003-target-infrastructure.md)을 따른다.

## 10. 운영 전 필요한 검증

Supabase와 목표 인프라의 월 비용·운영 책임 비교는 [ADR-003 목표 인프라 선택](ADR-003-target-infrastructure.md)을 따른다. 다음 검증은 대안 B 안에서 기능별 전환과 최종 제거를 시작하기 위한 완료 조건이다.

### Database

- 테이블별 행 수, DB 전체 크기와 일일 쓰기량 확인
- `auth.uid()`, RLS, Function, Trigger와 Extension의 이식성 분류
- 임시 PostgreSQL로 `pg_dump`·restore 리허설
- 기존 UUID, FK, timestamp와 업무 결과의 정합성 검증

### Auth

- 누적 계정 3,000명의 이메일·익명·Apple·Kakao 사용자 비율 확인
- 대상 Auth의 password hash 가져오기와 OAuth 계정 연결 지원 확인
- 기존 JWT·refresh token 유지 가능 여부 확인
- 재로그인, 비밀번호 재설정과 계정 병합 사용자 흐름 POC

### Storage

- 3개 Bucket의 객체 수, 전체 크기와 최대 파일 크기 확인
- 앱·DB에 저장된 공개 URL과 객체 경로 사용 범위 확인
- S3 호환 복사 리허설과 객체 수·크기·checksum 비교
- 새 URL 또는 CDN 전환 시 기존 앱 버전 호환성 검증

### 운영

- 허용 가능한 점검 시간과 도메인별 쓰기 중단 시간 결정
- 한 명이 구현할지 추가 개발·QA·인프라 인력이 있는지 확인
- B·C·D별 실패 시 롤백 가능 시점 정의
- 새 PostgreSQL·Auth·Storage 후보별 월 비용과 운영 책임 비교

## 11. 결정 규칙

검증 결과를 다음 기준으로 판단한다.

- Auth·Storage 호환성이 낮고 사용자 재로그인을 당장 허용할 수 없으면 B에 가중치를 둔다.
- 도메인 간 데이터를 분리할 수 있고 짧은 기능별 쓰기 중단이 가능하면 C에 가중치를 둔다.
- 전체 리허설 환경, 추가 인력과 충분한 점검 시간을 확보하면 D를 검토한다.
- DB·Storage 데이터량이 작아도 Auth 세션 전환이 검증되지 않으면 즉시 전체 제거를 결정하지 않는다.
- 예상 작업량뿐 아니라 같은 기능을 두 번 이전하는 비용과 운영 중 장애 범위를 함께 비교한다.

## 12. 현재 결정

**대안 B를 채택한다.**

```text
Phase 0~도메인 이전
Flutter → Spring REST·STOMP → 기존 Supabase Auth·Database·Storage

마지막 안정화 단계
Flutter → Spring REST·STOMP → 독립 Auth·PostgreSQL·Object Storage
```

- Spring 기능과 인프라 이전을 분리하여 장애 원인을 좁힌다.
- 2주 챌린지 진행 중 기능별 전환과 롤백이 가능하도록 한다.
- 신규 Spring 코드는 Supabase 전용 기능에 의존하지 않는다.
- 최종 제거를 미루는 것이며 제거 목표를 취소하지 않는다.
- 불가피한 전환은 새벽 1시에 리허설된 Runbook에 따라 수행한다.

각 기능의 운영 전환은 ADR-003의 STOMP 부하 테스트, 데이터 검증과 전환 리허설을 통과해야 한다. Auth·Storage 이전 POC가 실패하면 대안 B 안에서 최종 제거 일정과 대상 제품을 다시 조정한다.
