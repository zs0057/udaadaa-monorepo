# 07. 구현 주의사항과 추가 검토가 필요한 항목

> 상태: 진행 중 — Phase가 끝날 때마다 이어서 갱신한다.
> 목적: "일단 동작하게는 만들었지만 완전히 해결하지 못했거나, 나중에 반드시 다시 봐야 하는" 항목을 한 곳에 모은다. 각 Phase 문서의 "선행 조건과 위험" 절에도 같은 내용이 흩어져 있지만, 이 문서는 Phase를 넘나드는 항목을 한눈에 보기 위한 것이다.

## 읽는 법

- **위험도**: 방치하면 실제 장애·데이터 오염으로 이어질 수 있으면 "높음", 기능은 정상 동작하지만 설계상 부채로 남는 것이면 "중간", 알고 있으면 되는 수준이면 "낮음".
- **해결 시점**: 이미 계획된 후속 Phase가 있으면 그 Phase를, 아직 담당 Phase가 없으면 "미정"이라고 적는다.

## 전체 공통

| 항목 | 위험도 | 내용 | 해결 시점 |
|---|---|---|---|
| 로컬 Spring 빌드 미검증 | 중간 | 이 세션(샌드박스)에는 Java 21이 없어 Claude가 직접 `./gradlew test`를 실행하지 못한다. Phase 1부터 4까지 전부 사용자가 로컬 터미널에서 직접 빌드·테스트를 돌려 확인해야 실제로 컴파일·통과 여부가 확정된다 | 매 Phase 구현 직후, 사용자 로컬에서 |
| 실기기 회귀 테스트 전체 보류 | 중간 | Task #8. Phase 0~4 전부 시뮬레이터(Phase 3 스모크 테스트 1회 제외)·통합 테스트 기준으로만 검증됐다. 실제 iOS/Android 실기기에서의 동작은 전체 마이그레이션(Phase 0~8) 종료 후 한 번에 몰아서 확인하기로 결정된 상태다 — 문제가 생기면 어느 Phase에서 유입됐는지 특정하기 어려워질 수 있다 | 전체 Phase 종료 후 |
| `flutter analyze` 미실행 | 낮음 | Phase 1부터 매 Flutter 전환마다 "사용자 로컬에서 실행 필요"로 남아있고, 이 세션에서 실행 여부가 확인된 적이 없다 | 사용자 로컬에서, 아직 미확정 |

## Phase 3 (Chat + Notification)

| 항목 | 위험도 | 내용 | 해결 시점 |
|---|---|---|---|
| `service_role` 키 유출 | 높음 | `post-initial-chat-data`/`stage-post-initial-chat-data` Edge Function에 하드코딩돼 있던 `service_role` 키. 코드 수정은 끝났지만 실제 키 로테이션(Supabase 대시보드에서 키 재발급)은 별도로 진행해야 한다 — 재배포만으로는 이미 노출된 키 자체가 무효화되지 않는다 | 미정(운영 작업, 사용자 확인 필요) |
| 기존 `message-push` DB Trigger 유지 중 | 중간 | Spring Notification 모듈은 코드상 완성됐지만 `FCM_CLIENT_EMAIL`/`FCM_PRIVATE_KEY`가 비어 있어 실제로는 아무 것도 안 보낸다. 기존 Trigger를 지우지 않은 채 병행 중이라 지금은 안전하지만, 두 경로를 언제 전환할지(자격 증명 채우기 → 검증 → Trigger 제거)는 아직 실행되지 않았다 | Phase 8(의존성 제거) 또는 별도 운영 작업 |
| STOMP 연결 자체는 자동 테스트로 검증 안 됨 | 낮음 | 저장 API·멱등성은 MockMvc로 검증했지만 실제 WebSocket 핸드셰이크·CONNECT 인증은 통합 테스트가 커버하지 않는다. 2026-08-07 스모크 테스트로 한 번 실사용 검증했으나 자동화된 회귀 테스트는 아니다 | 미정 |

## Phase 4 (Challenge)

| 항목 | 위험도 | 내용 | 해결 시점 |
|---|---|---|---|
| Challenge가 `feed`·`weight`를 직접 읽음(CHA-04) | 중간 | Record가 아직 Spring으로 안 넘어와서 임시로 Challenge 모듈이 Record 소유 테이블을 읽기 전용으로 직접 조회한다. Notification이 `profiles.fcm_token`을 직접 읽는 것과 같은 기존 패턴이라 새로운 위반은 아니지만, Phase 5에서 Record가 전환되면 이 직접 조회를 이벤트 구독으로 반드시 교체해야 한다 — 안 하면 두 모듈이 서로의 테이블을 계속 직접 넘나보는 구조가 굳어진다 | Phase 5 |
| `mission_complete` RPC가 `challenge`를 안 건드림 | 중간 | 미션 인증(Flutter → RPC)이 성공해도 `challenge` 테이블은 갱신되지 않는다. Flutter가 인증 직후 `updateMission()`(=`GET /challenges/me` 재조회)을 호출해야 진행 상태가 반영된다 — 이 호출이 실패하거나 누락되면 사용자가 화면을 다시 열 때까지 진행률이 갱신되지 않는다. Phase 3~4 이전부터 있던 근본적으로 같은 종류의 갭이며, Phase 5가 `mission_complete`를 대체하기 전까지는 구조적으로 해결 불가 | Phase 5 |
| `challenge.room_id` 백필 안 됨 | 낮음 | 이번에 추가한 `room_id` 컬럼은 기존 행에는 채우지 않았다(기간과 사용자만으로는 어느 방이었는지 100% 확정할 수 없는 케이스가 있을 수 있어서). 과거 참여 기록에 대해 "이 참여가 어느 방이었는지" 조회가 필요해지면 별도 데이터 정리가 필요하다 | 미정, 실제 필요할 때 |
| 성공 판정이 "조회 시점에만" 반영됨(compute-on-read) | 낮음 | `GET /challenges/me`를 호출해야 성공 조건 충족 여부가 계산·저장된다. 사용자가 마지막 날 미션을 완료하고 앱을 아예 안 열면 `is_success`가 영영 `false`로 남는다(원래 클라이언트 로직도 같은 한계가 있었음 — 새로운 회귀는 아니지만, 서버 배치·이벤트 기반으로 바꾸면 더 견고해질 수 있는 지점) | 미정 |
| 동시 다중 챌린지 참여 제한 없음 | 낮음 | 한 사용자가 여러 챌린지 방에 동시 참여하거나 일반 참여+방 참여를 동시에 갖는 걸 막지 않는다(기존 앱 동작 그대로 유지 — Phase 4에서 새로 제한을 추가하지 않기로 결정) | 의도된 동작, 필요 시 별도 논의 |
| 온보딩 7일 버그 수정의 소급 영향 미확인 | 낮음 | 온보딩 경로가 7일로 만들던 기존 챌린지 참여 데이터가 이미 운영에 쌓여있을 수 있다(과거에 온보딩으로 참여한 사용자는 애초에 성공이 불가능했던 상태). 이번 수정은 신규 참여부터 14일로 만들 뿐, 과거의 실패한 7일짜리 참여 데이터를 소급 정리하지는 않는다 | 미정, 필요 시 데이터 정리 |
